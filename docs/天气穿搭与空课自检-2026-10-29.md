# 天气、穿搭与空课显示自检

日期：2026-10-29。本次发布包含以下本地修复和界面验收内容。前端资源版本：20261029-3。

## 结论

“准备明天的衣服”原本默认使用明天的逐小时预报，日期筛选本身没有把今天替代明天。问题集中在预报依据不明显、活动时段处理、跨日和刷新，以及衣橱任务混在同一长页。天气源的真实预报误差还不能仅凭这次代码检查确定。

课表原本只显示两门课之间的间隔，首课前、末课后、全天未排课都缺少直观表达。用户不应该靠列表的空白来推断空课。

## 确认的问题与修复

| 问题 | 本地修改后的行为 |
| --- | --- |
| 天气日期、地点、参考时段藏在折叠说明中 | 准备页直接显示“明天 · 月日 星期”、地区、气温/体感/降雨概率、预报时段和获取时间；首页标明“今日日间预报” |
| 体育课也使用07:00—22:00最低体感，下午热、夜间冷时可能选得过厚 | 运动换装按体育课真实区间取相交小时预报；分开的两次体育课不把中间空档混入 |
| 校园跑没有时段，却容易被理解为已按跑步时间判断 | 保留全天参考，并明确说明跑步时段尚未设置；不推测跑步时刻 |
| 运动AI上下文仍可能拿全天天气，分钟区间被服务端过滤 | AI读取对应运动天气；14:00—15:40等有效分钟区间可传递到服务端 |
| 选计划、设置跑步、调用AI都会锁住日期 | 今天/明天保持相对日期并随跨日变化；只有手动选择其他日期才固定；提供“改日期”入口 |
| 准备明天与记录实穿共用日期 | 分为“准备穿搭 / 穿搭记录 / 衣物洗晒”；实穿默认记录今天，可补记过去日期 |
| 天气停留较久不自动更新、失败后等待过久 | 可见页面按缓存周期检查，失败后限速重试；显示旧预报/失败原因，过期不继续参与搭配 |
| 旧地区慢请求挤掉新地区缓存，忙碌状态吞掉新地区请求 | 各地区独立缓存；只持久化最新请求地区；修改、导入或跨标签更新地区都会请求当前地区 |
| 跨日后预计收衣日还停在旧默认值 | 未手动改动的默认收衣日随日期推进；人工填写值保留；预计日期不自动等于可穿 |
| 隐藏录入草稿让另一个工作区无法跨日更新 | 隐藏工作区保留草稿但不挡住当前工作区；切回后恢复编辑保护；打开的弹窗和进行中的AI请求继续受保护 |
| 改单件衣物状态需要进入详情 | 单件提供“放入待洗→开始洗→已晾晒→收好可穿”的下一步按钮；批量洗晒和状态调整保留 |
| 首屏日期控件、说明、重复天气占据太多空间 | 改日期默认折叠；衣物按类别和名称排列；次要设置弱化；375像素标准字首屏可见“选这套” |
| 首尾及全天空课不可见 | 手机课表增加上午/下午/晚间1—10节占用条，连续未排课节次合并为一行 |
| 空课、课间和午间混在一起 | 明确显示“第几节未排课”；大课内10分钟休息保留在课程明细；午间独立分隔 |
| 无课日、跨季节周可能套用整周首门课的作息 | 按选中日期解析作息；原始节次缺失、作息不明、超出导入范围时标记待确认 |
| 首页不容易看到当前空课 | 当前课程卡下方仅显示当前/下一段未排课的小节与起止时间，可进入完整课表；后续课程继续按课程合并 |

“未排课”只描述当前导入课表，不等同于个人有空。已有活动和个人安排继续在日历中查看。

## 实际验证

- 25个测试文件全部通过，63个JavaScript文件语法检查通过。
- 日期测试使用今天32℃、明天12℃、后天22℃的隔离预报，确认各日期不会串用。
- 覆盖体育课下午热/夜间冷、分钟边界、多个体育时段、未设跑步时段、旧缓存、失败重试、地区请求乱序。
- 浏览器验证了选计划与实穿日期分离、35分钟后自动刷新、跨日推进、隐藏录入数量草稿保留及默认收衣日推进。
- 验证了首次录入两件衣物后进入准备页，以及单件从待洗到收好可穿的操作。
- 验证手机课表有课日和全天未排课，正常字与深色200%字；补充横屏与桌面宽度检查。
- 线上`/api/weather`只读检查返回200，地区为福州仓山附近、时区Asia/Shanghai，覆盖2026-10-29至10-31。此结果确认接口数据口径，不证明实际气象准确率。
- 操作验收使用独立资料，未修改个人事项和衣橱记录，也未读取密钥和AI口令；未进行付费AI调用。AI测试使用固定响应，不代表真实模型准确率。

界面截图中的衣物与温度是验收示例，不能作为当天真实天气。

## 设计依据与参考

1. [Open-Meteo官方文档](https://open-meteo.com/en/docs)：逐小时数据、时区与每日汇总有不同口径。本程序日常穿搭参考07:00—22:00，手机天气软件可能显示全天极值；这可能造成数值差异，但尚未针对用户当时的两份预报做同地点、同小时对照。
2. [NN/g：Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)与[移动端次要内容后置](https://www.nngroup.com/articles/defer-secondary-content-for-mobile/)：本次采用按任务进入、先显示关键内容、设置按需展开的方式。它们是可用性研究和设计指导，并非穿搭模型效果的实验背书。
3. [FullCalendar开源项目](https://github.com/fullcalendar/fullcalendar)及[TimeGrid文档](https://fullcalendar.io/docs/timegrid-view)：参考时间占用与事件列表并用的表达。本项目使用现有小节模型实现轻量占用条，没有为了这一功能引入整套日历依赖。
4. 本地`ui-ux-pro-max`用于复核内容优先级、渐进呈现、触摸目标、暗色和大字适配；实际手机截图与操作结果作为验收依据。

## 后续建议：先收敛，再增加功能

1. **明日准备只给一个主要决定。** 默认一套，允许展开备选；展示为什么适合、还缺哪件。日常与运动需要换装时再分开，不让用户先完成长问卷。
2. **把天气从一天一个数改为必要时段。** 后续可展示上学、体育课、晚间的简短温差提示，给出“外层可脱穿”这类调整。当前全天穿搭仍参考07:00—22:00，而不是用户的实际外出起止时间。
3. **记录后再学习偏好。** 选择计划、确认实穿、评价感受是不同信号。先积累可解释的偏好统计；不能把几次点击或穿着次数称为已经训练出可靠的个人模型。
4. **洗晒围绕可用性。** 继续让用户确认干透；将“未来体育课是否有可用短裤”放在相关准备处。若要预测备用是否够用，还需要确认换洗和重复穿着习惯。
5. **空课可以成为安排入口。** 下一步可点击未排课段预填活动时间，再核对通勤、已有活动和截止事项；目前先保持占用提示清楚，避免给每段空课额外增加卡片。
6. **天气源偏差单独验证。** 用相同地点、日期和小时对照预报与实际感受；再决定是否增加天气源选择。仅更换API无法修复日期、时段和缓存逻辑。

暂不增加衣物照片识别、自动排满空课、频繁提醒或更多首页模块。先用这版验证三个基本操作是否足够顺手：明天选一套、今天记一次、洗晒点下一步。

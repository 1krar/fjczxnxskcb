# 常驻提示、每日一句与穿搭反馈闭环

日期：2026-10-23，北京时间。状态：代码自检、资料核实与功能构思；本轮未修改或部署程序。当前已部署版本为 `1bf82c0`。此前已确认的按课程合并、要记得默认一条、两模块折叠排序、轻标题与天气层级，继续沿用，仍待实施。

## 1. 这轮需求如何连起来

- 常驻事项长期保存，在相关课程、时间或准备场景轻量出现。
- 每日一句综合可用信息，自然选一个话题，不给每句强行附上同一条事项。
- 穿搭可以从多个方案中选择，并记录实际穿着、次数和评价，逐步形成个人偏好。
- 数据的意义需要分清：长期保留不等于时时催促；选中不等于实际穿过；穿得多不直接等于喜欢；穿过不自动等于待洗。

## 2. 每日一句复读：本轮确认的代码证据

### 已确认

1. `js/daily-model.js` 的 `chooseAdvice`：最高优先级达到80时，只保留同一最高优先级的候选。某条事项权重100时，即使有日常轻建议，手动换句也可能只在同一事项的两种措辞之间轮换。
2. 用虚构的当天截止事项做只读复现，候选中存在事项与一般评论；连续四次选择／换句的来源均为该事项。未读取浏览器真实个人记录。
3. `dailyFacts` 会将未完成的前几条事项反复送入AI上下文，无日期便笺也可进入。`server/ai-service.js` 提示词还优先强调综合要记得。
4. AI客户端保存的近期历史主要是句子文本，没有稳定的事项／主题重复记录。事实编号目前采用位置索引 `item:0`，不适合跨次判断是不是同一件事。
5. 现有衣橱只保存单品、常用搭配、跑步安排和偏好；没有完整的推荐曝光、选择、实际穿着和评分记录。

### 尚不能确认

代码没有发现“每句后固定追加数学公式”的专用拼接步骤。首页直接展示模型或本地候选返回的句子。未取得用户当时的真实回包和本机状态，因此不能把上述机制当作那一次复读的完整定位，也不能凭此断言AI未启用。

### 修正方向

- 将普通便笺、长期提示与有截止的任务分开。长期事项默认仅在关联场景出现，不自动成为每日一句必带内容。
- 给AI足够的课程阶段、天气、活动、准备和事项上下文，让它选一个最适合当前的话题；全面体现在考虑充分，不要求一句话包含所有信息。
- 记录稳定的来源ID、主题和最近提及时间。手动“换一句”应尽量更换主题；普通事项进入主题冷却，只有显著的时效变化才重新提高优先级。
- 让用户能对某个话题选择“少提这件事”；保留独立的提前提醒，不靠每日一句反复承担硬提醒。
- 本地备用建议同样需要主题轮换，避免AI失败后再次掉回同一个高优先级循环。
- 一般性轻评论可以没有具体事项来源；事实性主张仍应有依据。不要为了凑来源把公式、任务或地点附加在末尾。
- 更新时清理／迁移旧句子缓存，保留每天自动一次与现有调用上限；不因每分钟刷新数据就产生新付费请求。
- 模型遗漏主题字段时仍保留可用的句子，逐步补齐辅助信息；不把普通的表达变化变成新的“校验未通过”。

## 3. 常驻提示：长期记着，关联时轻提醒

### 录入与关联

在现有事项上增加“长期记着”的选项，搭配少量可选关联：

| 关联 | 场景 | 示例呈现 |
| --- | --- | --- |
| 某门课 | 课前、当前课、课程详情 | 数学课下方的一条“常记”便笺，长公式点开看 |
| 相对课程时间 | 体育课前、明日准备、出发准备 | “体育课带短裤”跟随对应课程，而非每天霸占首页 |
| 日期或时间段 | 特定工作日、某段晚上 | 只在匹配时段出现，允许选择提前量 |
| 已知教学楼／区域 | 下一次课在艺新楼等 | 根据课表地点给准备提示，不假定掌握GPS位置 |
| 不限定 | 事项页长期保留 | 默认不反复占据首页首条；用户可明确选择首页常驻 |

AI可以从自然语言提出关联课程或时段，使用现有课程清单帮助理解；录入不应要求用户写完整、标准的通知。关联不清时先保留原话，不扩大成所有课程都提醒。

### 展示规则

- 默认弱于临近截止或需要出发的事项，不占“要记得”唯一的高优先级预览。
- 相关位置先显示一行轻文本，长内容和多条便笺点开；不增加大标题栏和独立大卡。
- 同一课程／时段里避免重复冒出同一提示。看过后可以“今天收起”，但不代表永久完成。
- 可以暂停、修改关联或停止常驻。课程结束／学期切换后允许归档，不悄悄删内容。
- 常驻提示默认不进入每日一句的固定话题池；匹配场景也不要求AI复述它。
- 当前先讨论页面内提示。关闭网页后的系统推送需独立能力，不能把页面渲染当作已实现后台提醒。

## 4. 穿搭日志：先记录真实发生的事

### 轻量日常流程

1. 推荐先给约3套有差异的候选：一套熟悉的组合、一套换个搭法、一套适合当天活动的选择。实际数量以可穿库存为准，不凑不存在的组合。
2. 点“选这套”记录计划。可以替换某一件，或直接记录自己搭的另一套。
3. 点“今天穿了”确认实际穿着；支持补记日期和修改，不把明天计划自动计入今天的穿着次数。
4. 可选1—5分评分。再提供少量原因标签：好看、舒服、偏热、偏冷、运动方便、不适合雨天；不要求每次写说明。
5. 一天能记录日常和运动换装两个时段。共用单品的统计应按明确口径去重。

### 值得直接看的统计

- 近7天／30天穿过几天。
- 最近一次穿着日期、距离上次穿着多久。
- 连续穿着天数与记录的穿着时段次数。
- 上次确认洗涤之后的穿着记录。
- 一套搭配的平均评价与明确反馈次数，不把未评分当0分。

“穿过几天”与“穿过几次”分开：同一天日常和运动都用了同一件，按天计一次，按时段计两次。重复点确认、补改记录或撤销不得重复累计。天气保存为当时使用的预报摘要及状态，不当作实测暴露温度。

### 与洗晒联动

- 使用真实单品编号，两个同款运动短裤仍是两件独立衣物。
- 实际穿着后可选择“仍可穿／移到待洗”，不替用户统一作决定；穿用次数不给所有类别套一个卫生阈值。
- “洗了、晾晒、确认干透、穿过”是不同事件；预计隔天收衣不等于已干。
- 洗涤历史应落实到具体单品；现有全衣橱的 `lastLaundryAt` 不能当作每件衣服的上次洗涤时间。没有历史时显示未知，不补造次数。
- 轮换提示参考近期穿用、明后天体育课、两套短裤和当前洗晒库存。需要重复使用时说明条件，不假设同一件衣服能同时占用或一定来得及干。

## 5. 让推荐逐渐适合自己

### 每种反馈分别使用

| 数据 | 能说明什么 | 不应直接推断 |
| --- | --- | --- |
| 展示过的候选 | 用户有机会看见它 | 没选就是不喜欢 |
| 选中某套 | 当时有穿它的意向 | 已实际穿过／已经喜欢 |
| 确认穿了 | 一次真实穿着记录 | 穿得多一定更喜欢 |
| 整体评分 | 对这一套、这一场景的明确评价 | 每个单品都同样喜欢或讨厌 |
| 偏热、雨天不适等标签 | 某类环境中的体验 | 所有季节、活动都不适合 |
| 穿了另一套 | 用户实际选择的替代方案 | 未选候选应该被永久降低权重 |

例如常穿运动短裤，可能来自体育课要求或其他裤子待洗；不能据此永久取消牛仔裤推荐。低分也可能来自偏热，不一定是配色不好看。

### 分阶段实现

第一阶段：记录历史和评价，用可解释的个人偏好调整候选排序，再把近期穿用、明确反馈和用户当天想法的摘要提供给千问。普通API调用不会自动更新模型权重，这可以在不微调大模型的情况下改善个性化。

第二阶段：有足够可用反馈后，评估小型个人排序模型；保留新组合的展示机会，防止越推越窄。候选需在可穿、天气、运动与换装约束下多样化。

第三阶段：只有数据规模与评测表明有价值时再考虑训练或微调。单个用户少量日志不宜直接照搬多人协同过滤或大型时尚模型；暂不设“记满N次就训练好”的门槛或承诺。

### 数据与评估

- 记录候选集合及展示次序、选中ID、替换单品、日期时段、实际穿着ID、评分／原因、当时天气摘要、活动和可穿库存快照；未记录的字段允许缺失。
- 日志与单品当前状态分开，支持修改、撤销和删除；备份迁移需保留新增数据，避免旧字段校验导致历史被静默丢弃。
- 看后续真实选择、实际穿着和舒适评价是否改善，不能只用“选中率升高”证明更懂用户；重复展示同一套也可能提高选择概率。
- 先做本机记录与可导出备份；跨设备同步可后续使用私有Cloudflare D1数据，不把个人穿着／作息日志放入公开GitHub。现有D1目前只做AI访问与用量控制，尚未保存衣橱历史。

## 6. 资料与适用边界

1. [Implementation intentions facilitate prospective memory under high attention demands（Memory & Cognition，2008）](https://link.springer.com/content/pdf/10.3758/MC.36.4.716.pdf)：研究把具体情境线索与待执行行为联系起来。可作为“在相关课程／时段提醒”的设计依据；实验任务不能直接证明本程序的效果。
2. [Hu、Koren、Volinsky：Collaborative Filtering for Implicit Feedback Datasets](https://yifanhu.net/PUB/cf.pdf)：讨论行为频次、显式评分和不确定性的区别。可借鉴“穿着频次不直接等于喜爱程度”；其多人协同过滤模型不是本项目第一阶段的直接实现方案。
3. [Wardrowbe 开源项目](https://github.com/Anyesh/wardrowbe)：README明确列出穿着历史、评分和搭配反馈，可参考功能划分，不要求迁移现有程序或使用其部署架构。
4. [Wardrowbe：Wear and Wash Tracking](https://wardrowbe.com/docs/wardrobe/wear-and-wash/)及[Wore Instead](https://wardrowbe.com/docs/suggestions/wore-instead/)：官方文档说明“选择后确认穿过”和记录实际替代搭配的流程。官网功能可能区分云服务与开源版本，不直接宣称仓库免费版包含全部流程；本项目自行设计轻量实现。

本轮区分心理学期刊研究、推荐系统论文与项目文档，未做国内核心期刊目录认定。未将开源项目功能描述作为个性化推荐有效率的科学证明。

## 7. 收敛后的实施顺序

1. 首先处理每日一句同源复读、近期主题记录和缓存迁移；长期便笺从普通截止任务中分离。
2. 实现常驻提示的关联与轻展示；同时落实此前已确认的紧凑首页布局。
3. 建立实际穿着日志、补记／撤销、近7／30天统计和多套候选选择记录。
4. 增加可选评分与原因，接入千问偏好摘要和个性排序；再评估后续训练需求。

本轮没有要求用户额外填写一轮问卷。评分维度、记录频率和长期提示关联都应允许逐步补充，不影响先记下来。

## 2. 继续沿用的已确认原则

- 首页优先展示当前／下一项、教室与时间，内容比模块名称醒目。
- 后续课程每次课一行，同名但不同时段／地点不能合并；真实小节和课间数据保留在主卡与详情。
- 默认顺序：当前主卡 → 要记得（一条）→ 后续课程 → 明日准备。要记得与后续课程可交换位置、独立折叠并记住偏好。
- 普通事项和长期便笺分开；不拿同一条数学公式给每句评论补结尾。
- 信息不完整也先保留可用部分；不催用户补齐资料，不因未标记完成就推断拖延。
- 衣物按真实单品计数，区分日常／运动换装、已确认可穿／预计收衣；穿过不自动移到待洗。
- 沿用福州仓山、北区到南区艺新楼约18分钟预算、早餐安排、攒两天一起洗／晚上晾晒隔天收、两套运动短裤等已有偏好。实际设置仍以用户保存值为准。
- AI继续使用用户已配置的百炼普通API北京地域，保留6位数字访问口令。

## 3. 第一批：记住设备与每日一句可靠性

### 3.1 已核实的问题

1. `js/ai-client.js` 的 `accessToken`、`saveAISettings` 使用 `sessionStorage` 保存访问口令；`aiEnabled` 又要求这里有口令。因此新标签页、会话结束等情况下可能重新锁定。不同浏览器的会话也不共享。
2. `requestDaily` 在请求模型前就写入 `automaticKey`。失败后，这个标记仍可能让后续调用认为当天已处理。内存中另有 `attempted` 与页面 `settled` 状态，需要一起调整。
3. 本轮使用隔离的内存存储和模拟503响应复现：请求失败后重新保存解锁信息，自动请求仍没有再次发出。模拟网络调用总数为1；未使用真实口令，也没有调用付费模型。

因此要同时修“解锁恢复”和“自动生成成功状态”，只增加一个保存开关不足以解决全部问题。

### 3.2 用户侧流程

- 解锁入口提供“记住这台设备30天”，作为明确可选项。这里的设备指当前浏览器／站点环境。
- 勾选并验证一次6位口令后，再次打开正式站自动恢复AI授权。
- 不勾选时，仅建立本次浏览会话的授权；浏览器恢复会话行为可能影响Cookie保留，服务端仍应设短期有效期。
- API设置清楚展示“已解锁”“记住至某日”“已过期／需要解锁”，避免把服务配置、访问授权与模型可用性混成一个状态。
- 提供“忘记本设备／退出AI”；可补充“撤销其他设备”。过期或主动退出后重新输入口令。
- 学校登录和AI解锁是不同流程，本功能只处理本网站AI访问。

30天是本轮规划默认值，后续可以改为7／30天选项；不增加一开始必须回答的设置问题。

### 3.3 建议的技术实现

- 输入口令时通过HTTPS验证，验证成功后签发高熵随机设备会话。原始口令不进入长期本地存储。
- 使用同站点、`Secure`、`HttpOnly`、`SameSite` Cookie；记录设备时设置有效期。不在Cookie中保存6位口令或百炼密钥。
- 在现有D1绑定中增加会话表，只保存随机凭证的哈希、创建／到期／撤销等信息。采用随机会话即可，不要求用户额外配置一套登录供应商或新密钥。
- 请求校验服务端到期与撤销状态，保留同源检查和必要的CSRF防护；按当前所有者共享AI用量限制，不能每记住一台设备就重置配额。
- 会话按浏览器隔离；不绑定易变化的IP，避免校园网与手机网络切换导致反复解锁。不把浏览器Cookie描述为硬件指纹绑定。
- 前端保存授权状态而非读取原始Cookie内容；页面启动时通过免费状态检查恢复授权，状态确定后再触发每日一句。
- 迁移旧会话和发布窗口内的旧页面调用，更新相关资源版本，避免新旧鉴权方式混用造成循环锁定。
- 正式站、本地预览、不同浏览器与QQ内置浏览器属于不同环境，不能承诺一次解锁到处通用。云端AI授权先以固定正式站为准。

### 3.4 每日一句自动运行

流程：打开页面 → 恢复设备授权 → 显示缓存或本地内容 → 判断今天是否已成功生成 → 满足条件时自动调用 → 成功后写入缓存。

- “已经尝试”和“成功生成”分开记录。失败、过期未授权或暂时离线，不等于当天已成功生成。
- 授权恢复、网络恢复后允许受限重试；使用退避和并发去重，不能无限重试或双标签重复请求。
- 配置／会话验证不消耗模型次数；真正调用模型继续使用现有每分钟2次／每天默认20次共享限制。
- 继续保持每日自动一次的产品意图；手动换句另计。重要记录变化时可显示当前本地内容并允许手动更新，不按每次时钟变化自动调用。
- “每天自动”在这一阶段表示每天首次打开／恢复页面后自动生成。网页关闭时在后台定时生成、推送，需要另一个服务范围，本阶段不承诺。

### 3.5 同批修复复读

- 参照上一轮已复现的同源候选循环，调整本地建议池。
- 给事项与话题稳定ID，保存近期主题／来源历史；长期便笺默认不反复加入每日一句。
- AI综合课程、天气、活动和事项，选择一个主题；普通评论可不引用具体事项，不为凑依据附加公式。
- 支持“少提这件事”；时效性提醒由对应事项和提前提醒承担。
- 清理／迁移已有自动生成与句子缓存，避免新逻辑上线后继续被旧缓存锁住。

## 4. 第二批：紧凑首页与视觉层级

1. 按一次课合并后续列表，当前课程第二小节留在主卡提示；小节与课间按真实时间展开。
2. 要记得默认显示一条，明确开始／截止含义。保留总数与展开入口，不重复铺出第二张临近事项卡。
3. 两模块放入统一顺序容器，上下排序同时改变DOM顺序，保证键盘与读屏顺序一致；事项内部顺序不被覆盖。
4. 标题降为轻标签、取消重复外框和整排操作。位置调整放入菜单，折叠入口易发现、点击目标足够大且互不重叠。
5. 日期附近显示轻天气摘要，区分日间范围和即时温度；必要时补时段／概率提示，详情中保留数据源、获取时间和刷新。
6. 记录折叠、模块位置等本机偏好；内容刷新不把布局重置。

## 5. 第三批：关联式常驻提示

- 增加“长期记着”，可选关联课程、课前／出发准备、时间段或已知教学楼。
- 在相关主卡、课程详情或准备处显示一行轻便笺，长内容点开；不再占据首页唯一的重要事项位置。
- 允许今天收起、暂停、编辑关联、取消常驻；看过与永久完成分开。
- 没有明确关联时先保留原话和用户选择，AI可提出建议，不把所有课程都当作触发条件。
- 沿用现有提前提醒，明确页面提示与关闭网页后的系统推送不是同一能力。

## 6. 第四批：穿搭记录、多方案选择与评分

- 推荐约3套有实际差异的候选；库存不足时按实际数量显示，不凑方案。
- 选择记录为计划；确认“今天穿了”才计入实际穿着，可补记、替换单品、记录自己搭的一套。
- 支持日常／运动换装，近7／30天穿过几天、时段次数、上次穿着与洗后穿用记录；重复点击与修改必须去重。
- 给整套可选1—5分评价，再选舒服／好看／偏热／偏冷等原因；不要求每次填写问卷。
- 实际穿用、洗涤、晾晒和确认干透分别记录，落实到具体单品；不拿全局洗衣时间代替每件衣服的洗涤历史。
- 日志保存候选集合、选中方案、实际方案和反馈，允许未评分和字段缺失；备份升级支持旧数据并保留新增历史。

## 7. 第五批：基于反馈的个性化

- 先做个人偏好排序和历史摘要，让千问参考近期穿着、明确评价、当天想法与活动约束。
- 分开对待展示、选择、实际穿着和评价。未选择不等于不喜欢，频繁穿着不直接等于最喜欢。
- 保留候选差异与尝试新组合的机会，避免一直推最常穿的两套。
- 数据与效果足够支撑时，再评估小型排序模型或微调；普通API调用本身不会自动训练模型。
- 用后续实际穿着、体验评价和修改量观察改善，不只看选择率。

## 8. 存储与服务分工

| 数据 | 本阶段建议 |
| --- | --- |
| 源码、测试、非个人示例、设计档案 | GitHub与现有Cloudflare发布链路 |
| 百炼API Key、访问口令配置 | 继续保留在Cloudflare服务端配置 |
| 记住设备的随机授权凭证 | 当前浏览器Cookie＋D1会话记录 |
| AI用量 | 继续由D1服务端统一控制 |
| 事项、衣橱、实际穿着与评价 | 第一阶段先本机保存，纳入可导出备份 |
| 个人资料跨设备同步 | 后续私有D1方案，需独立的数据所有者标识与同步冲突设计 |
| 衣物照片等大文件 | 有实际需求后再考虑对象存储，本阶段不要求拍完整衣橱 |

“记住设备”只恢复访问授权，不自动同步浏览器中的课表更新、事项或衣橱。两者在设置文案中应区分，避免让用户误以为换设备已有同一份记录。

## 9. 验收与交付顺序

每批以可检查的完整结果交付，验证后沿用GitHub → Cloudflare发布，不把构思样例当成完成。

| 批次 | 关键验收 |
| --- | --- |
| 设备与每日一句 | 勾选后重开正式站可恢复；未勾选遵守短期会话；过期／撤销失效；6位口令与限流仍有效；失败后可恢复自动生成；同一天刷新不重复付费；换句能换主题 |
| 首页 | 320／390px与宽屏长课名可读；剩余课不重复成多行；默认一条事项；模块折叠／排序保持；实际点击目标不重叠；天气不抢主内容 |
| 常驻提示 | 仅关联场景出现；不挤掉紧急事项；今天收起不永久删除；时间含义与提前量准确 |
| 穿搭日志 | 选择不等于穿过；补记／修改／撤销正确；同款单品独立；日常／运动计数口径清楚；洗晒状态不被擅自改变；备份可恢复 |
| 个性化 | 明确评价能改变合适场景下的排序；未选方案不被误判；可穿和运动约束始终满足；推荐保留差异 |

自动化测试优先覆盖会话到期／撤销、鉴权与配额、失败恢复、主题去重、小节边界和日志统计。涉及Cookie持久化、移动端布局与手势时需实际浏览器验收。当前会话此前存在浏览器自动化访问限制，尚未解除；不能用语法检查代替这部分验收。

暂不根据没有验证的工作量给出固定工期。实施时按上述批次顺序推进，有具体阻塞再调整，不在每个小步骤重复征求确认。
